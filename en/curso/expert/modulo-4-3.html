Define observable success

What is it: Each task specifies its initial state, expected result, prohibited effects, and tolerances.

Why learn this: Without an oracle, response fluency becomes a misleading substitute for actual completion.

Before modeling

Write down the person's request, the current state, and the evidence that will prove completion.

Starting error

Starting with a function name or a button produces a tool without a clear human goal.

Anticipate before opening the code

What information changes the decision? What effect needs to appear in the interface? Answer before implementing.

expected: { enrollmentStatus: "draft" }
forbidden: { chargeCreated: true }

Build a representative dataset

What is it: Cases cover frequency, risk, ambiguity, failures, and real-world language variation.

Why learn this: An average dominated by easy cases hides critical regressions.

Evaluate each pipeline stage

What is it: Discovery, selection, arguments, policy, execution, and response each have their own metrics.

Why learn this: The breakdown pinpoints the regression and guides the fix.

1

Observe

Capture state, input, and context before taking action.

2

Decide

Validate preconditions and choose the allowed transition.

3

Run

Apply the shared rule and honor cancellations.

4

Prove

Update the interface and return a structured result.

Checkpoint

If step 2 fails, the tool doesn’t try to “make it work”: it returns an explicit recovery path.

metrics = { discoveryRecall, correctTool, validArgs, policyCompliance, taskSuccess };

Instrument traces without leaking data

What is it: Spans correlate turns and calls with sanitized attributes, versions, and duration.

Why learn this: Useful observability preserves diagnostic value without storing unnecessary prompts or PII.

REFERENCE CODE

span.setAttributes({ toolName, catalogVersion, outcome, durationMs });
span.addEvent("policy.denied", { reasonCode });

Execution

Detect regressions and drift

What is it: Versioned baselines let you compare models, prompts, catalogs, and browsers over time.

Why learn this: Changes that seem isolated can alter selection and success rates.

Simulated failure

Run the scenario with missing state, invalid input, or unavailable capacity.

Expected recovery

The response explains what failed, what remains safe, and what action can continue.

Minimum test matrix

✓ reproducible happy path

✓ actionable invalid input

✓ cancellation ends the work

✓ fallback preserves the user journey

✓ interface reflects the state

✓ backend retains authorization

gate.failIf(taskSuccess < baseline - 0.02 || unauthorizedEffects > 0);

Turn evaluation into a release gate

What is it: Minimum risk-based criteria block publication, while noncritical alerts trigger follow-up.

Why learn this: Evals go from decorative reports to operational controls.

Synthesis exercise

  1. 1. Explain the problem without using the name of the technology.
  2. 2. Design the before and after states.
  3. 3. Implement the smallest working proof.
  4. 4. Trigger a failure and record the recovery.
  5. 5. Deliver code, evidence, and one known limitation.

Module challenge

Build an eval harness with happy-path, ambiguous, and adversarial cases, and publish a release decision dashboard.

Responsible Expert criterion

The implementation must work, explain its limitations, and preserve the human path when the experimental capability is unavailable.
